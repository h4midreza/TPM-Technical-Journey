# Topic 8: Monitoring, Observability & Incident Management

## 1. Objective

Understand how infrastructure, applications, and data pipelines are monitored and how production issues are detected, investigated, and resolved.

This topic focuses on monitoring practices, observability tools, application and data reliability, alerting, incident management, and root cause analysis.

The goal is to understand system health, identify operational problems, investigate failures, and evaluate service and data reliability from a Technical Program Manager (TPM) perspective.

## 2. Practical Scenario: Data Platform Monitoring

Assume a Data Platform consists of several components:

| Component | Responsibility | Monitoring Consideration |
|---|---|---|
| NiFi | Ingests and routes data | FlowFile failures and processing queues |
| Kafka | Transfers events between services | Consumer lag and broker health |
| Document Processor | Processes documents | Processing latency and error rate |
| PostgreSQL | Stores metadata | Connections, query latency, and availability |
| MinIO | Stores document files | Storage capacity and request failures |
| ClickHouse | Stores analytical data | Query performance and data freshness |
| Kubernetes | Runs application workloads | CPU, memory, Pod health, and availability |

Monitoring must cover three main areas:

- **Infrastructure:** Resources and infrastructure availability.
- **Applications:** Application performance, errors, and service health.
- **Data Pipelines:** Data ingestion, processing, delivery, and freshness.

A service can be running normally while its data pipeline is delayed or producing incomplete data. Therefore, infrastructure and application monitoring alone are not sufficient.

## 3. Monitoring vs. Logging vs. Distributed Tracing

These three concepts provide different ways to understand system behavior.

| Concept | Main Purpose | Example |
|---|---|---|
| Monitoring | Tracks system health and performance over time | CPU usage increases to 90% |
| Logging | Records application and infrastructure events | PostgreSQL connection failed |
| Distributed Tracing | Follows a request across multiple services | Tracks a request from API to Kafka and PostgreSQL |

### Monitoring

Monitoring uses metrics and alerts to detect known problems and abnormal behavior.

Example: Alert when Kafka consumer lag exceeds an expected threshold for several minutes.

### Logging

Logging records events generated by applications and infrastructure.

Example: Metadata API logs an error when it cannot connect to PostgreSQL.

### Distributed Tracing

Distributed Tracing follows a request as it moves through multiple services.

Example:

```text
Client Request
     |
     v
Metadata API
     |
     v
Document Processor
     |
     v
Kafka
     |
     v
PostgreSQL
```

Tracing helps identify which component introduces latency or causes a request to fail.

Common tools include OpenTelemetry and Jaeger.

## 4. Metrics, Logs, and Traces

These are the three main types of telemetry used in observability.

### Metrics

Metrics are numerical measurements collected over time.

Examples:

- CPU and memory usage.
- API request rate.
- Application error rate.
- Request latency.
- Kafka consumer lag.
- Pipeline processing rate.

Metrics are useful for dashboards, trend analysis, and alerting.

### Logs

Logs are timestamped records of events.

Example:

```text
2026-11-15 10:30:15 ERROR
Metadata API failed to connect to PostgreSQL.
Connection timeout.
```

Logs provide detailed information about individual events and failures.

### Traces

Traces describe the journey of a request across multiple services.

A trace contains spans representing individual operations and their durations.

A `Trace ID` helps correlate related operations across different services.

**Key distinction:**

- Metrics show what is happening.
- Logs explain what happened.
- Traces help identify where and how a request was affected.

## 5. Infrastructure Monitoring and Application Monitoring

### Infrastructure Monitoring

Infrastructure monitoring tracks the health and resource usage of the underlying environment.

Important metrics include:

| Metric | Purpose |
|---|---|
| CPU Usage | Measures processor utilization |
| Memory Usage | Tracks RAM consumption |
| Disk Usage | Monitors storage capacity |
| Disk I/O | Measures storage read/write activity |
| Network Traffic | Tracks incoming and outgoing traffic |
| Node Availability | Checks whether infrastructure nodes are operational |
| Pod Restarts | Identifies unstable workloads |

For example, high memory usage on a Kubernetes Node may affect multiple application Pods.

### Application Monitoring

Application monitoring focuses on application behavior and performance.

Important metrics include:

- Request Rate
- Error Rate
- Response Time
- Request Latency
- Active Connections
- Application Availability
- Failed Requests

For example, Metadata API may be running, but its response time may increase because PostgreSQL queries are becoming slower.

Infrastructure monitoring helps identify resource-related issues, while application monitoring helps identify application-level problems.

## 6. Data Observability

Data Observability focuses on the health, quality, and reliability of data as it moves through pipelines.

Traditional application monitoring cannot detect every data problem.

For example, Metadata API may return successful responses, but ClickHouse may not have received the latest events.

### Important Data Observability Indicators

| Indicator | Description |
|---|---|
| Data Freshness | How recently data has been updated |
| Data Volume | Number of records received or processed |
| Data Quality | Validity, completeness, and consistency of data |
| Data Distribution | Changes in expected data patterns |
| Schema Changes | Unexpected changes in data structure |
| Pipeline Failures | Failed ingestion or processing operations |

### Example

Suppose a DMS pipeline normally receives 100,000 document events per hour.

Today, it receives only 15,000 events.

The application may still be running normally, but the data volume is abnormal.

Data Observability helps detect this type of issue.

## 7. Prometheus and Grafana Fundamentals

### Prometheus

Prometheus is an open-source monitoring and alerting system designed primarily for collecting and storing time-series metrics.

Its main responsibilities include:

- Collecting metrics from applications and infrastructure.
- Storing metrics as time-series data.
- Querying metrics using PromQL.
- Evaluating alerting rules.
- Sending alerts to Alertmanager.

Prometheus commonly collects metrics by scraping HTTP endpoints such as `/metrics`.

For example, an application can expose:

```text
http_requests_total 15000
process_cpu_seconds_total 320
```

Prometheus periodically collects these values.

### Grafana

Grafana is a visualization and dashboard platform.

It can connect to different data sources, including Prometheus, Loki, and other monitoring systems.

Grafana is used to:

- Build monitoring dashboards.
- Visualize metrics over time.
- Compare application and infrastructure behavior.
- Display alerts and operational trends.

### Prometheus vs. Grafana

| Tool | Main Responsibility |
|---|---|
| Prometheus | Collects, stores, and queries metrics |
| Grafana | Visualizes metrics and creates dashboards |
| Alertmanager | Groups, routes, and manages Prometheus alerts |

Example:

Prometheus collects CPU usage from Kubernetes Nodes, while Grafana displays CPU utilization across the cluster.

## 8. Centralized Logging and Log Search

Applications and infrastructure generate logs in different locations.

Centralized Logging collects these logs into a common platform so that teams can search and investigate them.

### Typical Logging Architecture

```text
Application Logs
       |
       v
Log Collector
       |
       v
Log Storage
       |
       v
Log Search and Visualization
```

Common technologies include:

| Tool | Responsibility |
|---|---|
| Fluent Bit | Collects and forwards logs |
| Logstash | Processes and transforms logs |
| Elasticsearch | Stores and searches logs |
| OpenSearch | Search and analytics platform |
| Loki | Log aggregation system |
| Kibana | Visualizes and searches Elasticsearch logs |
| Grafana | Visualizes logs from supported data sources |

### Practical Example

If Document Processor fails while processing a document, the team can search centralized logs using:

- Timestamp
- Service name
- Document ID
- Error message
- Trace ID

This makes troubleshooting easier than accessing each application server separately.

Logs should also have appropriate retention policies, access controls, and protection for sensitive information.

## 9. Health Checks and Service Readiness

Monitoring must distinguish between a running application and an application that is ready to serve requests.

Important health checks include:

- **Liveness:** Checks whether the application is functioning.
- **Readiness:** Checks whether the application can receive traffic.
- **Startup:** Allows sufficient time for application initialization.

Kubernetes uses these probes to manage Pod health and service availability.

For example, Metadata API may be running, but if it cannot process database-dependent requests, its Readiness Probe should prevent it from receiving traffic.

### Service Health vs. Data Health

These are not the same.

| Service Health | Data Health |
|---|---|
| API responds successfully | Latest data has arrived |
| Pods are running | Expected records are present |
| Database connections work | Data is complete and consistent |
| Application is available | Pipeline is processing on time |

A service can be healthy while its data is stale, incomplete, or incorrect.

## 10. Alerting Rules and Alert Routing

An alert is generated when a metric or condition indicates a potential problem.

### Alerting Rules

Alerting rules define the conditions that trigger alerts.

Example:

```text
IF CPU Usage > 85%
FOR 5 minutes
THEN Generate Alert
```

Another example:

```text
IF Kafka Consumer Lag > 10000
FOR 10 minutes
THEN Generate Alert
```

Thresholds should be based on normal workload patterns and operational requirements.

### Alert Routing

Alert Routing determines which team or person receives an alert.

For example:

| Alert | Responsible Team |
|---|---|
| High CPU on Kubernetes Node | Platform Team |
| Metadata API Error Rate | Application Team |
| PostgreSQL Availability | Database Team |
| Kafka Consumer Lag | Data Platform Team |
| MinIO Storage Capacity | Storage Team |

### Alerting Considerations

- Avoid too many unnecessary alerts.
- Group related alerts.
- Assign clear ownership.
- Define escalation rules.
- Prioritize alerts based on severity and impact.

An alert should ideally identify the affected component, observed condition, severity, and required action.

## 11. Service Reliability and Data Pipeline Metrics

### Error Rate

Measures the percentage of failed requests or operations.

Example:

If 100,000 API requests are received and 2,000 fail, the error rate is 2%.

### Latency

Measures the time required to process a request or operation.

Common measurements:

- Average Latency
- P95 Latency
- P99 Latency

P95 means 95% of requests complete within that latency value or faster.

Percentiles help reveal slow requests that averages may hide.

### Throughput

Measures how many requests, records, or events are processed within a period.

Examples:

- API requests per second.
- Documents processed per minute.
- Kafka events consumed per second.

### Availability

Measures the percentage of time a service is available or successfully handles eligible requests, depending on the defined SLI.

For example, 99.9% monthly availability represents a 0.1% unavailability allowance.

### Pipeline Success Rate

Measures the percentage of records or pipeline executions that complete successfully.

Example:

If 10,000 records are ingested and 9,800 are processed successfully, the processing success rate is 98%.

### Data Freshness

Measures how up-to-date the available data is.

For example, if the latest available event is two hours old, data freshness is two hours behind the expected current state.

### Data Volume Anomalies

Detects unexpected increases or decreases in incoming or processed data.

Example: A pipeline normally processes 50,000 records per hour, but suddenly processes only 5,000.

### Consumer Lag

Consumer Lag represents the difference between the latest messages available in Kafka and the messages processed or committed by a consumer.

High lag may indicate:

- Consumer is slower than the producer.
- Consumer instances are unavailable.
- Processing time has increased.
- Downstream dependencies are slow.

Consumer Lag is generally measured in messages or offsets. It should be considered together with processing rate and event age.

## 12. SLA, SLO, and SLI

These concepts define and measure service reliability.

### Service Level Indicator (SLI)

An SLI is a measurable indicator of service performance.

Examples:

- Availability.
- Error Rate.
- P95 Latency.
- Pipeline Success Rate.
- Data Freshness.

### Service Level Objective (SLO)

An SLO is a reliability target defined for an SLI.

Example:

- API availability should be at least 99.9%.
- P95 API latency should remain below 300 ms.
- Data freshness should be less than 15 minutes.

### Service Level Agreement (SLA)

An SLA is a formal agreement defining service expectations between a provider and a customer.

It may include availability commitments, support response times, and consequences for failing to meet agreed targets.

### Comparison

| Concept | Meaning | Example |
|---|---|---|
| SLI | What is measured | API availability |
| SLO | Desired reliability target | 99.9% availability |
| SLA | Formal service commitment | 99.5% contractual availability |

SLOs help teams manage reliability internally, while SLAs define external commitments.

## 13. Incident Severity and Escalation

An Incident is an event that causes or may cause service degradation, interruption, or data reliability problems.

Incidents should be classified based on impact and urgency.

Example severity levels:

| Severity | Description | Example |
|---|---|---|
| SEV1 - Critical | Major service outage or critical business impact | Entire Data Platform unavailable |
| SEV2 - High | Major functionality degraded | Document processing stopped |
| SEV3 - Medium | Limited impact or partial degradation | Increased API latency |
| SEV4 - Low | Minor issue with limited impact | Non-critical monitoring warning |

### Incident Escalation

Escalation ensures that the appropriate teams are involved when an incident requires additional technical expertise or management attention.

A typical process:

```text
Incident Detected
       |
       v
Initial Investigation
       |
       v
Impact and Severity Assessment
       |
       v
Responsible Team
       |
       v
Technical Escalation
       |
       v
Resolution and Recovery
       |
       v
Incident Closure
```

A TPM helps coordinate teams, track dependencies, communicate impact, and monitor recovery progress.

## 14. Root Cause Analysis (RCA)

Root Cause Analysis identifies the underlying reason an incident occurred rather than focusing only on its visible symptoms.

### Example

A Data Platform pipeline stops processing events.

Initial observation:

Kafka Consumer Lag is increasing.

Investigation:

1. Kafka brokers are available.
2. Consumer Pods are running.
3. Processing latency has increased.
4. Document Processor memory usage is unusually high.
5. Containers are repeatedly restarting because of OOMKilled.

Possible root cause:

Document Processor consumes more memory than its configured limit during high-volume processing.

### RCA Techniques

- **5 Whys:** Repeatedly asks why a problem occurred to identify underlying causes.
- **Fishbone Diagram:** Organizes potential causes into categories such as People, Process, Technology, and Environment.
- **Incident Timeline:** Records the sequence of events and actions.

### RCA Evidence

A reliable RCA should use evidence such as:

- Application logs.
- Infrastructure metrics.
- Distributed traces.
- Kubernetes events.
- Deployment history.
- Configuration changes.
- Pipeline execution history.

RCA should focus on system and process improvements rather than assigning personal blame.

## 15. Corrective and Preventive Actions

After identifying the root cause, teams define actions to restore service and prevent recurrence.

### Corrective Actions

Actions that fix the identified problem.

Examples:

- Increase an appropriate memory limit.
- Fix inefficient document processing.
- Restore failed Kafka consumers.
- Correct database connection settings.

### Preventive Actions

Actions that reduce the likelihood of similar incidents in the future.

Examples:

- Add memory usage alerts.
- Improve automated testing.
- Introduce load testing.
- Review resource requests and limits.
- Implement better monitoring for processing delays.
- Improve deployment and rollback procedures.

### Practical Monitoring Design

For a representative Data Platform pipeline:

```text
Data Sources
     |
     v
    NiFi
     |
     v
   Kafka
     |
     v
Document Processor
     |
     +-------> MinIO
     |
     v
 PostgreSQL / ClickHouse
     |
     v
    BI
```

Monitoring should cover three levels:

- Infrastructure metrics: CPU, memory, disk, network, and Pod health.
- Application metrics: error rate, latency, throughput, and availability.
- Data metrics: ingestion success, processing delay, consumer lag, data volume, and freshness.
